# ADR-0001: 框架定位与设计哲学

- 状态: APPROVED（2026-08-28，irylex 人工评审通过）
- 日期: 2026-08-28
- 决策者: irylex（人类确认）

## Context（背景）

Synonz 是 irylex 开发的纯 Rust、开源（Apache License 2.0）的 Agent 工程框架，
愿景是覆盖从单 agent 到多 agent 编排（orchestration）的完整场景。

现有框架格局：

- Python 阵营：LangChain、AutoGen、CrewAI 等，功能丰富但存在长期被社区
  诟病的工程问题；
- Rust 阵营：Rig、Swiftide 等各有侧重，尚无覆盖"单 agent 到多 agent 编排"
  全场景的成熟框架。

目标用户群体确认为两类：

1. Rust 应用开发者——在产品中集成 agent 能力（编码助手、自动化、智能服务等）；
2. 平台/基建团队——需要可嵌入、可定制、可控的 agent 基础设施。

## Problem（问题）

Synonz 为什么存在？它的身份是什么？在着手任何架构设计之前必须先回答这个
问题，否则后续所有决策缺乏裁决标准。经过对现有框架痛点与 Rust 语言能力的
对照分析，得到如下痛点清单：

| # | 现有框架痛点 | 具体表现 | Rust 语言是否自动解决 |
|---|---|---|---|
| P1 | 过度抽象、复杂度失控 | 层层包装、框架魔法、debug 困难 | 否——Rust 框架一样可以过度抽象 |
| P2 | 行为不可预测、不可控 | 隐式状态、隐藏 prompt、魔法默认值 | 否——架构问题 |
| P3 | 性能与部署 | GIL、打包地狱、无法单二进制部署 | 是——语言红利 |
| P4 | 类型安全缺失 | schema/配置为运行时校验的动态值 | 是——语言红利 |
| P5 | 生命周期与取消语义缺失 | 无法干净取消、资源清理随意 | 否——需架构级设计 |
| P6 | 可观测性不足 | tracing 是后期外挂而非内生 | 否——需架构级设计 |
| P7 | 测试困难 | 难以确定性测试，依赖大量 mock | 部分——依赖架构设计 |

关键观察：P3/P4 选择 Rust 即免费获得；P1/P2/P5/P6 是**架构问题**，Rust
不会自动解决——一个 Rust 框架完全可以重蹈覆辙。因此"承诺解决哪些痛点"
实质是在定义框架的架构级差异化身份。

## Decision（决策）

### 定位声明

Synonz 是**显式、可控、可观测的 Agent 工程基础设施**——不是"功能最多的
框架"，而是"你永远能推理出 agent 在干什么的框架"。

### 存在理由（优先级排序）

1. **架构级差异化**（框架身份，即四支柱）：
   - 反过度抽象（P1）——最小公开概念集、无框架魔法、行为透明；
   - 行为可控（P2）——状态显式、prompt 显式、用户能推理 agent 在做什么；
   - 生命周期完备（P5）——取消是一等公民，取消传播有语义，资源可靠清理；
   - 内生可观测（P6）——执行即事件，可观测、可回放。
2. **语言红利**（P3/P4）：性能、单二进制部署、编译期类型安全。
3. **生态价值**：填补 Rust 全覆盖 Agent 框架的空缺。

### 框架形态

采用"分层：核心抽象 + 可选实现"路线，并以"最小核心 + 渐进增长"
（Minimal Core + Progressively Growing）作为演进纪律：

- 抽象只为真实用例、强架构要求或已被验证的重复模式而引入；
- "全部覆盖"是终态愿景，不是第一步——先建立最小可演进核心，随场景增长；
- Pre-1.0 阶段 API 允许演进，核心契约须经真实使用验证后再稳定。

### 分层结构（终态视图）

```
模式层    ReAct / plan-execute / research 等运行模式
          （S3 场景驱动，v1 不预设抽象）
组合层    Agent：一种罐装组合（model + tools + prompt + 循环）
原语层    Model / Tool / 事件流 / Message —— 全部公开
```

### 四支柱作为验收标准

后续所有功能设计以四支柱为裁决与验收标准。

## Alternatives Considered（备选方案）

### 形态选择

- **薄抽象层**（只定义 trait 与组合机制，不提供实现）：Rust 惯用但要求
  用户自行实现一切，开箱体验差。被否决。
- **厚运行时框架**（配置即用，类 LangChain/AutoGen 的 Rust 版）：开箱快
  但重蹈"框架魔法"，与四支柱冲突。被否决。
- **分层：核心抽象 + 可选实现**：底层公开契约，上层提供可选实现。被采纳，
  并进一步收敛为"最小核心 + 渐进增长"。

### 附加收益说明（非独立决策）

- P7（测试）：未列入四支柱，但 P6 的"执行即事件、可录制回放"天然为
  确定性测试铺路，属免费副产品。

## Consequences（后果）

### 正面

- 框架身份清晰，四支柱构成设计评审与实现验收的统一标准；
- 与现有框架形成实质差异（架构级而非功能级），而非"Rust 版 LangChain"；
- 渐进增长纪律防止早期抽象固化错误。

### 成本与义务

- 每个新功能必须对照四支柱论证，便利性让位于可推理性；
- 文档必须让行为显式可推理（无魔法意味着一切需文档化）；
- 可观测性是发布标准，不是附加项。

### 风险

- 相比"厚运行时"框架，初期开箱便利性较低（显式选择的代价）；
- 最小核心若在真实使用中暴露设计错误，pre-1.0 阶段需要破坏性调整
  （可接受，但须尽早通过真实场景验证核心契约）。

### 关联

- 四支柱的具体落点见 ADR-0003（可观测）、ADR-0004（取消）、
  ADR-0007（行为显式）。
