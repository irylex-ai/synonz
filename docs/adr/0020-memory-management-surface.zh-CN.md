# ADR-0020: 记忆管理面与条目语义——应用面/内部分离、同权原地更新与不复活边界

- 状态: DRAFT（待 irylex 评审后转 APPROVED）
- 日期: 2026-09-19
- 决策者: irylex（人类逐点确认；本 ADR 每个决策均经弹窗逐项确认，
  遵循 `.opencode/rules/architecture.md` §5–§9 的渐进决策流程）
- 性质: 记忆管理能力新增 + `Memory` 公开面重切 + 存储契约破坏性扩展；
  破坏性变化随 0.6.0 单波发布
- 关联: 细化 ADR-0012（记忆与上下文系统——三层模型与分层哲学保持，
  本 ADR 在其上增加"条目管理面"）、ADR-0017（事件总线与反应架构——
  新增管理事实词汇）、ADR-0019（上下文引擎扩展面——策略槽只读、
  写入收口、`MemoryReader` 只读物料面；本 ADR 细化其构造归属）
- 版本承载: 0.6.0（工作标签；发布准备时按纳入范围定号）

## Context（背景）

0.5.0 发布后的实际开发中暴露：**记忆只能"追加与下沉"，不能被用户
管理**。当前形态是——L1 按轮追加、溢出压实为 L2 并弹出源 L1；L2 按
批追加、溢出蒸馏为 L3 并弹出源 L2；会话终结时剩余 L2 机械促进为 L3；
L3 按身份三元组 upsert。整条链没有任何"指明一条记忆并修改/删除"的
手段：条目没有标识、没有删除入口、没有统一视图，而 `Memory` 把
`l1_append` / `l1_pop_oldest` / `l2_append` / `l3_upsert` / `l3_query`
等**分层原语**直接暴露给应用。

这带来三类问题：①用户/应用无法纠正错误记忆、无法遗忘；②公开面把
内部机制（层的写法与弹出语义）冻结成长期契约，机制演进等于破坏应用；
③应用可以绕过沉淀链直接写层，破坏"记忆由对话沉淀"的单一来源模型。

业界的主流记忆系统（记录级 `list/search/edit/delete`、按作用域批量
删除、无内容审计事实）与 JVM 分代的心智一致：**应用管理"记忆条目"，
分层是内部存储与策展机制**。本 ADR 的目标即在此。

决策过程按架构规范渐进展开：先定寻址与条目边界，再定标识、动词与
保证边界，随后是公开面切分、存储契约、分页与新鲜度，最后是机制、
事实与 API 形态（详见各 Decision 小节）。

## Problem（问题）

1. **不可寻址**：条目无稳定标识；L3 以身份三元组为键（同身份覆盖）、
   L2 是追加序列（`pop_oldest` 从头部移除，位置漂移）——"删这一条 /
   改这一条"在类型上无法表达；
2. **不可遗忘**：L3 完全没有删除路径；L1/L2 只有"沉淀用"的位置弹出，
   且没有会话级 / subject 级清理；
3. **机制外露**：应用可直接按层读写，绕过沉淀链；机制变更会破坏
   公开应用面；
4. **"遗忘有效"的真实威胁**（已核对事实前提）：派生完成后源材料即被
   消费（压实弹 L1、蒸馏弹 L2），**同源重建不会发生**；真实漏洞只有
   在途维护竞态、新证据重观测与应用主动重建三类——因此需要的是
   **有序保证**，不是永久语义黑名单；
5. **不可观测**：条目被编辑 / 删除没有事实，无法审计、无法定位问题。

## Decision（决策）

### 1. 寻址模型：条目级、层无关

管理操作寻址"记忆条目"——层无关、带稳定标识的对象；**分层降为
内部的存储与策展机制**（哪些内容落 L1/L2/L3、何时下沉，是机制而
不是应用的关注点）。应用面对的是条目，不是层。

### 2. 条目边界：持久条目 = L2 情景 + L3 事实

- **可管理条目**：`Episode`（L2——一段轮次窗口的摘要，情景记忆）与
  `Fact`（L3——跨会话的事实/偏好/结论，语义记忆）；
- **L1 是原始材料**（工作记忆），不进入管理面；
- **事实聚合（跨条目的同一性归一）不进内核**：它需要语义判定
  （可能引入模型、token 成本随记忆量增长、误合并风险），作为**策略
  能力**——自定义 `MemoryDistiller` 可用"查询 + 管理动词"实现合并/
  取代，应用也可用"搜索 + 批量遗忘"近似；
- 依据：L2 是 L3 的上一层且终结时会促进为 L3，用户对"那段时期的
  摘要"也有管理诉求；把它排除会让管理面缺失情景层。

### 3. 条目标识：框架生成的不透明 id

- `L2Entry` / `L3Entry` 增加 `id` 字段：条目创建时由框架生成、对应用
  不透明、随条目持久化；**编辑后 id 不变**；
- 理由：管理地址必须与内容、位置、存储实现三者无关；结构化派生
  标识（位置/指纹）会漂移，存储原生句柄会把地址绑死在存储上；
- 实施注：生成方案（进程内唯一、无新依赖）属实现细节。

### 4. 管理动词集

- `list`（分页枚举）/ `get`（按 id）/ `edit`（原地替换内容，保留
  id、类别与来源）/ `forget`（单条 + 批量过滤）；
- `search` 在 v1 由 `list` 的关键字过滤表达（语义搜索留待后续）；
- 每次修改发**无内容事实**（见 §14）。

### 5. 保证边界：立即不可见 + 在途有序 + 重观测算新证据

- 管理操作返回后，**所有后续读路径**（管理视图、装配与召回、维护
  链）不再看见该条目；
- 框架保证**在途维护不回写**（不会把已删来源的产物写出去，见 §13）；
- 用户重新说出已遗忘的事实 = **新证据**，允许生成新条目（遗忘不是
  永久语义黑名单）；
- **不承诺内容优先级**：谁后写谁生效（见 §6）；错误覆盖是**策略
  质量**问题（摘要/蒸馏的算法、提示词、写入前是否用 reader 对账），
  在策略层修复，框架以事实保证可发现；
- 物理删除、副本、备份、加密擦除归**存储实现**（契约 rustdoc 与
  扩展指南立法）。

### 6. 同权与统一机制：原地更新、不分来源

- 同一身份槽（`subject + conversation + topic`）**一条条目**；
- 写入**不分来源**——用户编辑与系统摘要/蒸馏都是**原地更新同一条**
  （id 不变）；内核不区分来源、不做人工标记、无优先级；
- 依据（irylex 评审意见）：人工优先/标记是把内容质量问题塞进内核，
  让机制复杂且掩盖真正的质量问题；人也会错、系统也会错，二者同权，
  内核只保证机制正确。

### 7. 公开边界：应用面 / 内部分离

- **`Memory` = 应用面对象**：管理动词（subject 按调用传递，见 §15）；
- **分层机制迁入 crate 内部对象**（承接现有 `Memory` 的分层原语与
  三存储槽聚合；命名实施时定，避免与 `MemoryL*Store` /
  `MemoryStoreError` 撞名）；引擎、Runtime、后台维护任务使用内部对象；
- `MemoryReader` **类型保持公开**（策略槽的只读物料面），**构造入口
  内部化**（见 §16）；`MemoryL1/L2/L3Store` 保持公开（存储扩展点）；
- 依据（irylex 评审意见）：公开面只留"开发者该用的"，机制藏进内部
  才能自由演进（JVM 心智：应用从不手动搬分代）。

### 8. 应用注入：不提供日常新增

- **新增只来自对话沉淀**（用户在日常对话中表达 → 引擎维护生成条目）；
  不提供应用侧 `add`；
- 测试 / 下游 fixtures：`test-util` 特性下的**种子入口**（与
  `MockModel` 同一模式，另含 reader 自测入口）；
- 批量导入 / 迁移：由应用**自持存储句柄**在框架外完成（文档化边界：
  框架不感知、无事实、无有序保证）；
- 依据：避免"第二来源"（对话沉淀 vs 应用注入）带来的溯源、质量责任
  与长期维护；真实需求出现时再立项（§4 的排除项）。

### 9. 存储契约扩展：必选方法

- `MemoryL2Store` / `MemoryL3Store` **必选**新增：
  `get(subject, id)`、`update(subject, entry)`（按 id 原地更新）、
  `remove(subject, id)`、`list(subject, 单源 keyset 查询)`（subject
  范围枚举——管理面列表、搜索与批量遗忘的基础）；
- `MemoryL3Store::upsert` **行为契约更新**：同身份替换时**保留原 id**；
- 内置实现全部补齐；自定义存储按**迁移指南**补（破坏波承载）；
- **L1 不参与条目管理**（原始材料），契约不动；
- 依据（irylex 评审意见）：管理能力已是核心语义的一部分，契约应当
  要求它真实存在；"默认实现返回不支持"会制造"声称支持却不支持"
  的半支持状态，与保证要求真实能力冲突；且强制发生在 pre-1.0 破坏波，
  代价最小。

### 10. 分页模型：keyset（与 ConversationStore 同构）

- `MemoryQuery`（过滤：`kind` / 会话 / 时间范围 / 关键字；`after`
  游标；`limit` 有界）、`MemoryCursor`（单源位置 `updated_at + id`）、
  `MemoryPage<T>`（`items` + `next`）；
- 与 `ConversationStore` 的 `ConversationQuery/Cursor/Page` 风格一致；
- **`limit` 必须有界**：L3 跨会话无上限增长（L2 每会话有界且终结排空，
  L1 留存另行立项），没有分页的枚举一定会爆；
- 排序键 `(updated_at desc, id asc)`（见 §12）。

### 11. 列表顺序与补拉：结构序 + 不足补拉

- **结构序**：L2 块（Episode）在 L3 块（Fact）之前——L2 是 L3 的上一层，
  这是结构关系，不依赖时间戳；**块内**按 `updated_at` 倒序；
- **不足才跨源补拉**：先列 L2，页不满时继续从 L3 补足；一旦进入 L3
  阶段不再回头——**跨界只发生一次**；
- **阶段游标**：`MemoryListCursor { phase: Episodes | Facts, position:
  MemoryCursor }`（不需要复合游标）；`kind=Some` 时退化为单源路径；
- 明确语义：这是"源优先、源内时间序"，**不是严格全局时间序**（极端
  情况下刚促进出的新事实可能排在较老的摘要之后）；严格全局时间序
  （两源持续归并 + 复合游标）记为可加性后续。

### 12. 新鲜度语义：统一 `updated_at`

- 条目增加 `updated_at`：创建时 = `created_at`；**任何更新（用户编辑
  或系统更新）刷新它**；
- **列表块内排序、分页游标、召回排序统一使用 `(updated_at desc,
  id asc)`**；
- 迁移：已有条目 `updated_at = created_at`；
- 依据：编辑过的记忆应当"浮上来"，与 §6 的原地更新自洽；两套新鲜度
  语义（列表看更新时间、召回看创建时间）不可接受。

### 13. 有序机制：写入前按 id 重校验来源（内核内部）

- 维护任务（蒸馏、终结促进）的写入顺序纪律：

```
1. 重读来源（按 id）        ← 已删来源不交给策略
2. 调用策略（纯变换）       ← 策略槽零改动
3. 写前再按 id 校验来源集合
4. 一致  → 写入 + 按 id 删源（替代按位置 pop）
   不一致 → 丢弃本次产物 + 发无内容事实
```

- **策略槽零改动**：槽仍是"输入 → 输出"的纯变换，不需要知道删除、
  跳过、写回等机制；全部由内核处理；
- 不需要派生溯源：源条目在派生时即被消费（L1 不可管理、L2 蒸馏即
  弹出），"源还在、产物也在"的情形不可达；此前 ADR 讨论中
  "产物一并清理"的表述据此修正；
- 依据：无锁、无版本、无调度耦合；利用 §9 已具备的 by-id 读；
  串行化会耦合调度且跨会话复杂，CAS 会为不需要的优先级给公开契约
  增负。

### 14. 管理事实词汇

- 新增 `MemoryEvent::Updated { subject_id, kind, id }` 与
  `MemoryEvent::Removed { subject_id, kind, ids: Vec<String> }`
  （**不含内容**；批量 ids 受分页 `limit` 有界）；
- 维护跳过被删来源复用既有 `FlowFailed { stage, moment: Background }`
  （不新增词汇）；
- 依据：管理是用户可见的重要动作，事实应当直白、可按 id 审计；
  批量与单条同一形状；与既有 `TurnArchived` / `Promoted` 风格一致。

### 15. API 暴露形态：直接挂 `Memory`，subject 按调用传递

- `memory.list(&subject, query)` / `memory.get(&subject, id)` /
  `memory.edit(&subject, id, content)` / `memory.forget(&subject, scope)`；
- **不做 subject 绑定句柄**（依据 irylex 评审意见）：绑定只是把
  "选 subject"从每次调用挪到一次绑定，不能减少"想清楚用哪个 subject"
  的责任；调用点显式传 subject 信息更完整；少一个公开类型；
- `runtime.memory()` 仍返回运行时级 `Memory`（应用面）。

### 16. `Memory::reader` 构造内部化

- `Memory::reader` 的**构造入口内部化**（引擎经内部对象构造，随载荷
  交给策略槽）；外部不再自行构建；
- `MemoryReader` **类型保持公开**（出现在公开槽签名里：
  `ContextAssemblerInput.reader`、`MemoryDistiller::distill(reader)`）；
- 外部槽作者的单测路径（种子 + 构造 reader）归入 §8 的 `test-util`
  入口；
- 依据（irylex 评审意见）：开发者主要在策略槽上**使用**这个对象，
  不需要自己构建；构造内部化让 `Memory` 的公开面进一步收敛。

### 附：两个小项（细则）

- `MemoryItem` 视图字段：`id`、`kind`（`MemoryKind::{Episode, Fact}`）、
  `content`、`source { conversation_id, topic }`、`created_at`、
  `updated_at`；
- 批量 `forget` 失败语义：**逐条尽力执行**（单条失败不中断整批），
  返回移除数量与失败清单；事实按批发（`Removed { ids }`）。

## Alternatives Considered（备选与否决）

**寻址与边界**

1. **分层原语寻址**（沿用层方法、仅补删除）——否决：把层泄漏给应用，
   机制被公开契约冻结，跨层同一条记忆无法整体操作；
2. **来源寻址**（按会话/轮次/时间窗操作，框架重算）——否决：无法
   表达"只删这一条事实"；粒度粗、易误伤同源记忆；
3. **只把 L3 当条目**——否决：漏掉情景层（用户想管理"那段时期的
   摘要"时无处表达）；L2 是终结会促进成 L3 的过渡物，管理它有意义；
4. **三层统一条目（含 L1）**——否决：编辑 L1 = 改历史，与逐字保真、
   装配不读真相域冲突；
5. **内核事实聚合（跨条目同一性归一）**——否决：语义同一性判定进入
   内核（可能需要模型），token 成本随记忆量增长，误合并/误分裂风险
   高；应作为策略能力（本 ADR 保留其表达手段）。

**标识**

6. **结构化派生标识**——否决：L2 位置漂移、同秒撞车、内容指纹随
   编辑变化；"编辑同一条"无法表达；
7. **存储原生句柄**——否决：地址与存储绑定，换存储即失效，破坏
   "存储可替换"的抽象。

**公开面**

8. **保留分层写公开 + 另加管理句柄**——否决：公开面继续混装，机制
   仍被冻结在公开契约里；
9. **折中：只读层方法保留公开**——否决：半步收敛，公开面仍保留分层
   概念，后续还要再切一次；
10. **subject 绑定管理句柄**（`manage(&subject)`）——否决（irylex
    评审意见）：绑定不能替代"想清楚 subject"的责任，反而让调用点
    信息不完整；多一个公开类型无实际收益；
11. **`Memory::reader` 构造保持公开**——否决（irylex 评审意见）：
    开发者只"使用"不"构建"，构造内部化让公开面收敛；自测路径由
    `test-util` 承接。

**注入**

12. **提供日常 `add`**——否决：引入第二来源（对话沉淀 vs 应用注入）
    与溯源、质量责任；当前无已验证需求；
13. **受控 `import`/`seed`（框架内）**——本轮否决：真实需求（知识库/
    迁移）可由框架外导入路径满足，等出现真实需求再立项。

**存储契约**

14. **默认方法返回 `Unsupported`**——否决：制造"声称支持却不支持"
    的半支持状态，与保证要求真实能力冲突；旧实现生态尚未成型，强制
    成本低；
15. **独立能力 trait + 运行时检测**——否决：Rust 需 `Any`/上转型，
    公开面与实现复杂度高，对当前规模过度设计。

**分页与新鲜度**

16. **offset 分页**——否决：可变集合下删除导致跳条/重复；
17. **时间窗枚举**——否决：同时间戳多条边界难处理、与过滤组合复杂
    （时间范围保留为过滤条件）；
18. **跨 kind 严格全局时间序（两源持续归并）**——否决：复合游标 +
    持续归并复杂；"先 L2 后 L3、不足补拉"简单且覆盖实际用途；严格序
    可加性后续；
19. **仅列表用 `updated_at`、召回用 `created_at`**——否决：两套新鲜度
    语义，长期解释成本高；
20. **不引入 `updated_at`**——否决：编辑过的记忆不会浮上来，与
    "按更新时间排序"的诉求相悖。

**机制与语义**

21. **人工优先**（系统不覆盖用户编辑）——否决：把内容质量问题塞进
    内核；同权统一机制才是框架该有的样子；错误覆盖归策略质量并可
    观测；
22. **并存**（同身份槽允许两条：用户版 + 系统版）——否决：记忆重复、
    需要召回去重与合并策略；
23. **产物一并清理（派生溯源）**——修正：源在派生时即被消费，该情形
    不可达；不需要为兑现保证引入溯源；
24. **串行化管理与维护**——否决：耦合会话调度、跨会话复杂、管理延迟
    不可预期；
25. **存储级条件写 / 版本号（CAS）**——否决：契约增负；当前语义下
    只需"来源有效性"，写入前重校验已足够；
26. **事件聚合变体（`Administrated`）/ 不新增事实**——否决：可读性差 /
    与"不得静默"冲突。

## Consequences（后果）

**破坏项（0.6.0 单波）**

- `Memory` 公开面重切：分层原语（`l1_append` / `l1_pop_oldest` /
  `l2_append` / `l2_pop_oldest` / `l3_upsert` / `l3_query` / 各层
  `len`/`window`/`read`）离开公开面，迁入 crate 内部对象；
- `Memory::reader` 构造内部化（类型保持公开）；
- `MemoryL2Store` / `MemoryL3Store` 必选新增
  `get`/`update`/`remove`/`list`——自定义存储实现必须补齐；
- `MemoryL3Store::upsert` 行为契约更新：同身份替换保留原 id；
- 条目新增 `id` 与 `updated_at`（`non_exhaustive` 加字段；序列化
  向前兼容以"缺失即回退"处理）；
- 召回排序由 `created_at` 改为 `updated_at`；
- 应用不再能按层注入 / 读取记忆（`test-util` 与框架外导入为替代
  路径）。

**加性项**

- 公开类型：`MemoryItem`、`MemoryKind`、`MemoryQuery`、`MemoryCursor`、
  `MemoryListCursor`、`MemoryPage<T>`；
- 公开动词：`Memory::list` / `get` / `edit` / `forget`；
- 事实：`MemoryEvent::Updated` / `Removed`（无内容）；
- `test-util`：种子入口 + reader 自测入口。

**边界（本 ADR 明确不做）**

- 应用日常新增（`add`）——新增恒来自对话沉淀或框架外导入；
- 框架外导入的事实/有序保证——文档化边界；
- 物理删除、副本、备份、加密擦除——存储实现职责；
- L1 留存与会话级清理（此前已记录的存储卫生缺口）——另行立项；
- 严格全局时间序（跨 kind 归并）、语义搜索、事实聚合/矛盾消解——
  分别记为可加性后续与策略层能力；
- 错误覆盖的内容质量——策略质量，内核不设优先级。

**文档义务**

- v7 架构文档（0.6.0 目标形态，v6 转 SUPERSEDED）；
- 0.6.0 实施计划；
- 扩展指南更新（管理面用法、导入边界、自定义存储迁移清单、
  "错误覆盖归策略质量"的规则）；
- CHANGELOG（破坏项 + 迁移表）；README 指针更新；
- 迁移指南：自定义存储需补的方法与 `upsert` 保 id 语义。

**验证要求**

- **存储契约**：内置实现补齐 `get`/`update`/`remove`/`list`；按 id
  更新/删除；`upsert` 同身份替换保 id；
- **分页**：块内 `updated_at` 倒序；L2 块 → L3 块结构序；不足跨源
  补拉且跨界一次；keyset 游标在增删下稳定（不跳不重）；`kind` 过滤
  退化为单源；
- **并发防护**：删除与在途维护竞争时不回写（可控策略/模型的确定性
  测试）；被删来源不进入变换；部分来源被删时只处理幸存者；
- **同权原地更新**：编辑后 id 不变；系统同身份后续写入为原地更新；
- **新鲜度**：编辑刷新 `updated_at`，列表与召回同时生效；迁移缺省
  `updated_at = created_at`；
- **只读面**：`MemoryReader` 构造不可见（编译期），槽只消费；
- **事实**：`Updated`/`Removed` 发出且不含内容；维护跳过经
  `FlowFailed` 可见；
- **公开面**：`Memory` 不再暴露分层原语（编译期检查）；应用经
  `list`/`get`/`edit`/`forget` 完成闭环。
