# ADR-0010: High Level API 优先原则

- 状态: DRAFT
- 日期: 2026-08-29
- 决策者: irylex（人类确认）

## Context（背景）

v1（M0-M8）完成后的复盘讨论中，人类开发者提出方向性修正：框架"要奔着好用去的"，
太底层了不好。预期使用分布为 **80% 场景由 High Level API 解决，20% 特殊场景才
需要 Low Level 完全自控**，且未来 SDK/第三方应能扩展模式。M9（预设构造器）
是本原则的首次应用。

本原则与 ADR-0001 的"最小核心 + 渐进增长"不矛盾：High Level API 由 Low Level
原语**组合**而成，不是并列的重复实现；两者同为一等公民。

## Problem（问题）

未来每个功能设计讨论的默认倾向是什么？先交付最小底层抽象（极简主义），还是先
定义并交付 80% 场景的高层用法（易用优先）？此前的默认倾向偏前者，已造成
"模式层后置"在 DX 上的缺口。

## Decision（决策）

1. **先问 80%**：每个功能设计文档首先回答"80% 场景的高层用法是什么"，
   并优先交付该用法；
2. **组合而非重复**：High Level API 由 Low Level 原语组合实现，单一事实源，
   不引入与底层并列的重复机制；
3. **逃生口常在**：Low Level 原语保持公开，服务 20% 特殊场景，且是 High
   Level 的地基；
4. **四支柱优先**：便利性不凌驾四支柱（可推理性、可观测性、生命周期、
   反过度抽象）——High Level API 同样必须显式、可控、可观测；
5. **模式配方化**：模式类功能优先以"配方"交付（prompt + 参数打包 + 预设
   构造器），而非机制化（继承、钩子、可插拔接口）——组合优于机制，
   与 ADR-0007/ADR-0009 一致。

## Alternatives Considered（备选方案）

- **纯低层极简主义**（一切用原语自建）：与框架"好用"的定位冲突，被否决。
- **机制先行**（发布 LoopEngine 钩子层满足模式扩展）：钩子签名依赖 S2
  记忆/状态形态，现在设计即猜测；且历史反例（LangChain AgentExecutor
  钩子蔓延后被 LangGraph 取代）证明钩子机制维护成本高。被否决——模式
  扩展由预设构造器（普通函数，返回 AgentBuilder）承担，第三方模式 =
  发布一个含预设函数的 crate，零注册机制。

## Consequences（后果）

### 正面

- DX 对齐框架定位：开发者可明确选用模式（`Agent::research` 等），
  80% 场景无需理解循环内部；
- 预设全部可覆盖（返回 AgentBuilder），no-magic 不破：注入的 prompt
  全文进 rustdoc，`extend_system_prompt` 支持组合扩展，`system_prompt`
  支持整体替换；
- 第三方模式扩展零门槛：普通函数返回 AgentBuilder 即可，无需核心改动。

### 成本与义务

- 每个未来功能（S2 会话、S3 编排等）的设计文档须包含"80% 高层用法"
  章节，作为评审检查项；
- 预设 prompt 是框架面向模型的公开行为——内容进 rustdoc，升级预设
  prompt 视为行为变更，需在发布说明中显式标注；
- 高层便利性的边界仍是四支柱：任何"方便"不得以隐藏行为为代价。

### 关联

- 依赖 ADR-0001（四支柱）、ADR-0007（模式是组合）、ADR-0009
  （契约随场景晋升）；
- 首次应用：M9（`Agent::react` / `Agent::research` / `Agent::reflection`
  预设 + `AgentBuilder::extend_system_prompt`）；
- 后续 S2/S3 设计须引用本原则（"80% 用法是什么"）。
