# ADR-0018: 系统调度与生命周期完备——Scheduler、Monitor 与 shutdown

- 状态: APPROVED（2026-09-11，irylex 人工评审通过）
- 日期: 2026-09-11
- 决策者: irylex（人类逐点确认）
- 性质: 调度与生命周期地基——新增公开 `Scheduler` 组件与内部系统
  调度器、Monitor 空闲清扫（时间驱动的生命周期完备）、显式
  shutdown 收尾、ConversationStore 查询面升级；破坏性变化随下一
  单波发布
- 关联: 承接 ADR-0017 评审修订二⑦（Monitor 延期记录——本 ADR
  兑现）；关联 ADR-0011（会话模型与 ConversationStore 契约）、
  ADR-0004（在途执行边界与取消设施复用）、ADR-0015（终结收尾为
  Runtime 结构行为）
- 版本承载: 待定（下一破坏波）

## Context（背景）

0.3.0 发布后，ADR-0017 评审修订二⑦留下的过渡态成为生命周期完备
性的唯一缺口：

1. **空闲终结依赖应用纪律**：`conversation_idle_timeout` 配置存
   在、`sweep_stale()` 行为存在，但框架内没有任何调用方（全仓唯一
   调用方是验收测试）——不调用它，空闲会话就永远保持 Open，L2
   永不促进、维护表条目永存。已确认需求（irylex）：空闲超时的
   设计意图是实时监控。
2. **优雅停机缺失**：进程退场时没有任何收尾动作（会话终结、
   L2→L3 机械促进、观测队列排空）；观测是异步入队的，进程终止
   可能吞掉终局事实。
3. **崩溃无对账**：被强杀（SIGKILL）或断电遗留的孤儿会话（store
   中 `last_active` 陈旧、无任何运行时持有）没有被任何机制回收。
4. **无时间调度基础设施**：未来必然出现更多定时场景（开发者视角
   的“文件编辑后自动保存”、框架视角的资源维护）；没有统一设施，
   它们会各自发明线程与 timer，宿主执行资源也无法统一复用。
5. **存储查询面受限**：`list()` 全量拉回全部 state（含全部
   turns）再由框架过滤；sweep 随后对每会话 `Conversation::of()`
   二次加载；应用面也没有分页与检索——会话规模一大就不可行。
6. **清扫/停机路径的可靠性洞**：终结收尾的 drain 无限等待（挂死
   的后台任务会让终结路径永久挂起）；维护任务 panic 被静默吞没。

讨论历经多轮收敛：每会话计时器（否决）→ Runtime Shutdown Hook
（演化为显式 `shutdown()`）→ 时间调度组件的边界立法（触发与执行
分离）→ 宿主模型（W1：执行环境由宿主提供）。最终确认这是**两个
半边 + 一个共同基础设施**：运行期由 Monitor 时间驱动收口，退出期
由显式 shutdown 收口；Scheduler 是两者共享的时间调度组件——同时
以公开组件形态服务开发者的自定义定时场景。

## Problem（问题）

1. 生命周期不完备：空闲会话没有自动终结路径；崩溃孤儿没有对账
   机制。
2. 无优雅退出动作：进程退场时会话不收尾、观测事实可能丢失。
3. 系统机制依赖开发者纪律：缺口本质是“可以选择不调用”；修复
   不能复现这一形态（显式调用意味着系统机制无法确保）。
4. 无共享时间基础设施：多定时场景将各自造线程/timer。
5. 存储查询面不支持规模：无分页、无检索、全量拉取。
6. 终结路径无界等待、失败不可见：清扫与停机都建立在不牢靠的
   收尾之上。

## Decision（决策）

### 1. 范围总图与双半结构

本 ADR 以两个半边收口，共享一个新基础设施：

| 半边 | 机制 | 职责 |
|---|---|---|
| 运行期 | **Monitor**（系统调度器的首个注册任务） | 空闲会话自动终结（时间驱动）；崩溃孤儿对账 |
| 退出期 | **shutdown**（显式异步收尾） | 停止系统调度；终结本 runtime 拥有的会话；观测 flush |

三个自然分层（组件边界，§2）：

- **Scheduler**：决定“何时产生执行机会”；
- **Executor**（宿主 Tokio multi-thread worker pool）：决定“在哪个
  执行环境中运行”；
- **任务客户端**：决定“执行什么”。

0.3.0 的过渡态（`sweep_stale` + `conversation_idle_timeout` 维持
现状）在本 ADR 终结。

### 2. Scheduler 组件边界与概念模型

Scheduler 是一个独立的“时间驱动任务调度组件”，**不是** Timer、
线程或线程池本身。

**核心职责**：

- 接收任务及其调度规则（本期规则 = 固定周期）；
- 管理任务的下一触发时间（deadline）；
- 触发时产生一次执行请求（提交给 Executor）；
- 管理任务的调度生命周期：注册、触发、取消（暂停/恢复/状态为
  暂缓项，§10）。

**边界立法**：

- **Timer 是 Scheduler 内部的实现机制**，不是独立组件：时间等待
  （下一 deadline、单线程等待循环）由 Scheduler 内部承担；
- **线程池/Executor 不属于 Scheduler**：实际执行一律提交给共享
  执行环境；
- **触发与执行分离**：任务到达触发时间，只意味着它应被提交执行，
  不意味着已占用线程开始运行；实际开始时间可受执行资源不足影响
  （触发准时 ≠ 开始准时）；
- **任务不各自创建线程或 runtime**：多任务共享同一调度机制与
  执行资源；任务之间在时间触发上相互隔离——一个任务执行 30 秒
  不阻塞其他任务的触发，一个任务 panic 不杀死计时线程；
- **任务重叠语义属于 Scheduler 的调度策略**（§5），不是 Timer 的
  职责。

**术语立法**：

- **Scheduler（调度器）**：时间驱动任务调度组件；
- **Schedule（调度规则）**：任务的重复规则（本期 = 固定周期）；
- **Trigger（触发）**：deadline 到期的时点决策（提交执行）；
- **Executor（执行环境）**：实际运行任务的地方（宿主 worker
  pool）；
- **OverlapPolicy（重叠策略）**：同一任务触发重叠时的调度策略；
- **系统调度器 / 用户调度器**：内核态 / 用户态两种持有形态
  （§3）；
- **Monitor**：系统调度器上注册的空闲清扫任务（§6）；
- **会话表**：运行时的会话归属登记表（§8）；
- **flush**：观测队列排空屏障（§8）。

### 3. 双层主权：系统调度器与用户调度器

**系统调度器（内核态）**：

- Runtime（Global Runtime）build 时内部创建；计时机制随即就绪；
  绝不阻塞或改变 build 的正常同步创建流程；
- 系统任务（本期：空闲清扫）由框架内部注册；**不暴露注册入口**
  ——系统机制不接受开发者调度；
- 开发者至多只读：系统调度快照（/proc 风格：任务名、周期、策略、
  距下次触发、是否运行中；字段细节草案级）。

**用户调度器（用户态）**：

- 公开 `Scheduler::new(executor)`：开发者自建实例、绑定自己的
  执行环境，调度自己的任务（如“文件编辑后自动保存”等定时场景）；
- 与系统调度器是**同一实现类型**（dogfooding：系统客户是该组件
  的第一个真实用户）；
- 每实例一条计时线程（时间生命独立是该组件的语义）。

理由：系统级机制不应由开发者显式调用（显式调用意味着机制无法
确保）；系统资源与用户调度资源分属两个主权层，互不侵占。前期
共享池形态；开发者自建池已天然可达（传入自己 runtime 的
Handle），配套便利与文档化为后续项。

### 4. 时间模型与宿主模型（W1）

**时间模型**：

- **计时线程**：Scheduler 自持一条轻量专用系统线程——只做登记、
  deadline 计算、等待、触发、提交；不执行任何业务逻辑；不形成
  自己的 worker pool。计时线程与宿主 Tokio multi-thread worker
  pool 是两个不同层次。
- **首次触发 = 立即首触发**（tokio interval 惯例）：注册即触发
  一次，之后每周期；系统 sweep 因此在启动时即完成崩溃孤儿对账。
- **时钟与推进**：单调时钟维护 deadline；固定速率
  （`deadline += period`）带追赶保护（过载后按周期倍数跳到当前
  时间之后，不一次补发积压触发）。
- **隔离性**：触发决策与提交为非阻塞 handoff；某任务执行慢不
  阻塞其他触发；执行资源不足时开始时间延后（语义允许）。

执行时序：

```
Runtime build（宿主 async 上下文内或显式注入 Handle）
  → 捕获宿主 Executor Handle（W1）
  → 创建系统 Scheduler；注册系统任务（空闲清扫）
  → 计时线程启动（时间生命开始）
  → build 正常返回（不阻塞、不改变同步创建流程）

计时线程：等待下一 deadline → 触发（按 OverlapPolicy 判定）
  → 提交执行请求给宿主 Executor（非阻塞）
  → 宿主 worker pool 实际执行任务
```

**宿主模型（W1：执行环境由宿主提供）**：

- 执行提交经由宿主的共享 Executor（`tokio::runtime::Handle`）——
  计时线程只触发，执行在宿主 worker pool；
- **Handle 获取**：Runtime build 在宿主 async 上下文内调用时自动
  捕获（常规路径：`#[tokio::main]` 内 build）；同步构建场景经
  builder 显式注入；两者皆无的失败形态为实施草案级细节（见
  开放项）；
- Scheduler 不自持执行池、不与应用形成双池。

### 5. 并发策略（OverlapPolicy）

每任务一个策略参数，三种（`#[non_exhaustive]`）：

| 策略 | 触发时（上次未完成） | 完成回接 | 积压上限 | 适用 |
|---|---|---|---|---|
| **Skip** | 丢弃本次触发 | 清除占用 | —（无积压） | 清扫/巡检（错过一次无妨） |
| **Concurrent** | 立即再起一层（允许自我并发） | 各自独立结束 | 无界（受执行池容量兜底） | 每次都必须执行的独立作业 |
| **Queue（合并）** | 记一次 pending | 有 pending → 立即续跑；无 → 清除占用 | **1** | 必须完成但不允许自我并发（自动保存等） |

- Queue 为**合并语义**：运行中无论收到多少次触发，只合并为一次
  补跑；不做无界 FIFO 堆积——持续超载 = 背靠背连续运行，负载
  回落后不燃烧过期积压。若需要“每次触发都必须执行”，那是
  Concurrent 的语义。
- 实现落点（两处）：触发决策（提交/丢弃/记 pending）+ 完成回接
  （执行 wrapper 的 RAII guard：清除占用或续跑；panic/取消安全）；
  计时线程、提交路径、隔离机制三策略完全共用。
- 系统空闲清扫使用 **Skip**（上次未完成则本次无意义）。

### 6. Monitor：系统首个注册任务

- **任务形态**：周期任务、Skip 策略、立即首触发。
- **执行模型：集中扫描**——从 store 真相源查询（`list_stale`
  下推，§7）。会话表（§8）只做归属与后台任务，不承担过期发现。
- **为什么不是每会话计时器**：见备选与否决理由（同步构造墙、
  N 任务、持久化断裂、热路径抖动）。
- **崩溃恢复对账**：进程被强杀/断电留下的孤儿会话（store 中
  `last_active` 陈旧、无任何运行时持有）由下一次启动的系统 sweep
  的立即首扫发现并终结（`IdleSwept`）——这是非优雅路径的唯一
  恢复机制，也是 Monitor 兼任的职责。
- **分页循环**：逐页处理；游标越过失败条目，不阻塞同轮推进
  （失败条目下一 tick 重试）。
- **失败可见**：清扫路径的失败经总线以 `FlowFailed` 事实可见，
  永不静默。

### 7. 存储查询面（list_stale / list）

背景缺陷（Context 5）：全量拉回 + 框架过滤 + `of()` 二次加载；
无分页无检索。决策：

- **`list_stale` 下推**：框架计算阈值（`now - idle_timeout`；策略
  在框架），store 只做数据查询——返回“未结束且
  `0 < last_active <= before`”的会话；游标分页。默认 in-process
  store 内部线性扫描（引导级默认）；生产 store（SQL/Redis）可用
  索引下推。
- **`list` 查询面（保留并升级）**：元数据关键字（`id` /
  `subject_id` / `topic` 大小写不敏感子串）+ 游标分页；旧全量
  形态退役（签名与返回变化）。
- **游标（keyset）分页**：全序 `(last_active 降序, id 升序)`；
  `next` 精确指示是否还有下一页。不使用 offset/limit——清扫边
  遍历边终结（集合被修改），offset 会跳漏且失败条目会阻塞推进。
- **摘要返回**：两个查询返回 `ConversationSummary`（id、
  subject_id、topic、last_active、ended；不含 turns）；全量状态
  仍走 `load`/`of`。
- 查询类型 `#[non_exhaustive]` + 公开构造器（外部 store 实现者
  需能构造；构造器形态为草案级）。
- 破坏性 trait 变更随下一破坏波；`ConversationStore` 契约的变更
  通过 append-only 修订注记记录于 ADR-0011（本 ADR 批准后补录）。

### 8. shutdown 契约

- **形态**：`runtime.shutdown().await`——显式异步方法。Rust 没有
  可靠的进程退出钩子（见备选与否决理由）。
- **触发归属**：信号/正常结束的触发由应用决定（`select!` +
  ctrl_c/SIGTERM）；框架不截获全局信号。
- **收尾名单：统一会话表**——维护表升级为会话表：条目 = {会话
  句柄 + 后台任务}；`new` / `with_id` / `of` 登记，任何 end 路径
  移除；shutdown 快照该表。共享 store 下只收本 runtime 拥有的
  会话，不误杀其他 runtime/进程。
- **停机顺序**：

  ```
  runtime.shutdown().await
    ① 停系统 Scheduler（幂等；在途执行不等待）
    ② 快照会话表 → 逐会话 end_with(Shutdown)
         drain（有界）→ 机械促进 L2→L3 → 持久化 → emit Ended{Shutdown}
    ③ 观测 flush（内部屏障）→ 返回
  ```

- **幂等**：多次调用安全；首次执行，其余并发/后续调用等待其完成
  （不早退——否则调用者可能在收尾未完成时退进程）。
- **终态门**：不设新运行期状态门；契约外用法文档声明（“终结后
  拒绝续写”仍是 v4 已记录的延期项，不属于本 ADR）。
- **边界**：不等待在途前台 turn（应用应先静默再 shutdown）；
  崩溃孤儿不归 shutdown（由下次启动的 Monitor 对账）；与 sweep
  的并发竞争由 `end_with` 幂等性兜底。
- **观测 flush**：内部 `EventBus::flush()`（队列屏障 + oneshot
  确认，不进公开面）——保证 `Ended` 等终局事实在 shutdown 返回
  前已投递到观察者。
- **词表**：`ConversationEndReason` 增 `Shutdown` 变体（审计可
  区分 主动关闭 / 空闲回收 / 进程退场收尾）。

### 9. 前提工程：drain 有界化与 panic 可见化

清扫与停机都依赖终结收尾的可靠性；0.3.0 的两个洞必须在本波填平：

- **drain 有界化**：后台维护任务的等待有超时上限；超时后继续
  收尾流程（不再无界挂起），并发出 `FlowFailed` 事实。
- **panic 可见化**：维护任务 panic（JoinError）不再吞没，经总线
  以 `FlowFailed` 事实可见。
- 超时值等参数为实施草案级（§开放项）。

### 10. 公开面变更清单

**新增公开**：

- `Scheduler`（`Scheduler::new` 自建；调度；取消；自有任务只读
  信息）；
- `Schedule`、`OverlapPolicy`、`TaskHandle`（命名草案级）；
- 系统调度只读快照类型；
- 会话查询类型：`ConversationSummary` / 游标 / 分页结果 / 查询
  入参（命名草案级）；
- `ConversationEndReason::Shutdown`。

**变更**：

- `ConversationStore`：新增 `list_stale`；`list` 升级为查询面
  （签名与返回变化，旧全量形态退役）；
- Runtime：新增 `shutdown()`；build 启动系统调度（宿主 Handle
  捕获/注入）；
- 会话表（原维护表）内部结构升级。

**暂缓**（设计已预留，非破坏性可加）：pause/resume/status、
cron 类规则、一次性/延迟任务、自定义执行池配套便利、正文检索、
Scheduler 专用事件词条。

## Alternatives Considered（备选与否决理由）

1. **不做 Scheduler 组件，Monitor 内联循环**——否：宿主问题
   （时间生命、执行外置、重叠语义）会就地重复解决；后续时间驱动
   能力各自造机制；与“开发者可用的调度组件”目标不符。
2. **每会话计时器（Conversation 自持到期任务）**——否：
   `new`/`with_id`/`of` 全同步，无法 spawn tokio 任务；N 会话
   N 任务；持久化断裂（重载会话无计时器，仍需集中兜底）；热路径
   抖动（每 turn 重置计时器）。
3. **进程钩子 / Drop 收尾**——否：Rust 无托管运行时；`Drop` 不能
   await，同步标记会跳过 drain/促进、孤立 L2；SIGKILL/断电下任何
   钩子都不执行（Java shutdown hook 亦然）。强杀遗留由崩溃恢复
   对账覆盖，不能靠退出钩子。
4. **全自动隐式启动（build 内直接 `tokio::spawn` 计时器）**——否：
   build 同步签名与 tokio 上下文约束（panic/静默跳过/改签名三选
   一）；静默跳过 = 行为随环境状态变化（magic）。本 ADR 以“自持
   轻量计时线程 + 执行外置”取代。
5. **首次 async 调用采纳宿主（Z 形态）**——否：调度生命周期依赖
   首次 async API 调用，与 Runtime 语义不符。
6. **自持完整 runtime（W3）**——否：每实例一个执行池、与应用双
   池、不复用外部执行资源。本 ADR 只自持轻量计时线程。
7. **显式 `start_monitor()`（Y 形态）**——否：系统机制依赖
   开发者显式调用则无法确保（缺口复现）；“配置即点火”——
   `conversation_idle_timeout` 的配置本身即是声明意图，系统自
   送达。
8. **offset/limit 分页**——否：清扫边遍历边终结，offset 跳漏；
   失败条目阻塞推进；深翻页代价随规模增长。
9. **正文检索（turns/messages 内容匹配）**——暂缓：契约语义重
   （分词/大小写/排序），需 store 自建文本索引；元数据检索先满足
   需求，正文能力另立（或走 Memory L3）。
10. **shutdown 全库扫描**——否：共享 store 下误杀其他 runtime/
    进程拥有的活会话；归属登记才是正确范围。
11. **资源状态监督 / 后台健康监督 / 完整生命周期模型
    （pause/resume/status、cron）**——拒收/暂缓：无消费者、无
    场景；均为非破坏性可加。
12. **通用 Executor 抽象（自定义 Executor trait）**——暂缓：
    tokio Handle 直接够用；自建池已天然可达（传入自己的 Handle）。
13. **框架内置进程信号处理**——否：不截获全局信号；触发主权在
    应用（`select!` + ctrl_c/SIGTERM）。

## Consequences（后果）

**破坏性变化**（集中下一单波发布，迁移指引随 CHANGELOG）：

- `ConversationStore`：新增 `list_stale`；`list` 签名与返回变化
  （实现者需更新）；
- 新增公开类型与组件（`Scheduler` / `Schedule` /
  `OverlapPolicy` / `TaskHandle` / 查询类型 / 快照类型）；
- `ConversationEndReason::Shutdown` 变体；
- Runtime `build()` 的执行环境契约（宿主 async 上下文或显式注入）。

**行为变化**：

- 配置 `conversation_idle_timeout` 的 Runtime 在 build 后即拥有
  时间生命：空闲清扫自动进行（应用零调用）；
- 进程退场推荐显式 `shutdown().await`（应用以 `select!` 接线
  信号）；强杀/断电遗留由下次启动对账。

**依赖**：无新增（tokio / tokio-util 已在依赖中）。

**风险**：

- 每实例一条计时线程（多 Runtime 实例场景的资源成本；进程级
  环境通常一个）；
- `shutdown()` 的 flush 会等待观测投递（受观察者“必须快速返回”
  的既有契约约束）；
- 共享 store 多 runtime 的会话表归属边界语义需文档化；
- 时间语义（立即首触发、固定速率追赶、Queue 合并）需测试锁定。

**后续义务**：

- 下一版本实施计划（实施记录接续本 ADR）；
- v4 架构文档 §14 的 Monitor 延期记录更新为已兑现；
- 开发者自定义 Scheduler 示例（“文件编辑后自动保存”类场景）；
- 命名终稿按 coding.md §5 命名立法在实施期执行。
