# ADR-0031: 分层记忆的可恢复维护——持久化压实游标、蒸馏时间窗与一致性语义

- 状态: APPROVED（2026-10-24，irylex 人工评审通过；蒸馏沉淀窗口
  默认 1 天，经评审修订）
- 日期: 2026-10-24
- 决策者: irylex（逐项决策；遵循 `.opencode/rules/architecture.md` §3–§9
  的渐进决策流程）
- 性质: 组件契约 ADR——扩展 ADR-0026 §4（存储契约）与 ADR-0028 §2
  （批量压实）的维护生命周期；不改变分层模型、观察面与管理面
- 关联: 上游消费场景（Valkyrie 0.6.0：自定义持久化 L1/L2/L3 + 频繁
  重启 + 不终结会话）；ADR-0026 / ADR-0028 / ADR-0029
- 版本承载: 0.9.0（L1 存储契约破坏性变更）

## Context（背景）

组件的写侧维护由三处触发：窗口填满的后台压实（`spawn_task`）、主题
切换的蒸馏、会话终结的收尾（压实余量 + 蒸馏 + 限定向量修复）。这些
行为依赖一个"未压实轮次"的边界：进程内计数器在每轮归档时自增、压实
成功后清零，批次取"最近 N 轮"。

四个存储契约被明确定义为**持久化端口**（ADR-0026 §4/§8）：应用可以用
Redis / MongoDB / Neo4j / Milvus 或自定义文件存储替换进程内默认实现，
数据在进程重启后保留。这是受支持的持久化后端，而不是例外用法。

上游消费场景是"持久化存储 + 频繁重启 + 不终结会话"：会话必须保持
进行中才能跨重启续用（`runtime.shutdown()` 会终结会话，终结后的会话
不可续用），因此应用不调用终结；而维护边界只活在进程内，重启后归零。
其可观察结果是：L2/L3 始终为空、从未出现压实/蒸馏事件；即使最终以
`finalize` 收尾，进程内计数为 0、批次为空，也不会处理重启前已持久化
的轮次。

## Problem（问题）

维护边界（哪些轮次尚未压实）必须**持久化**，否则：

- 重启后组件不知道积压，批次退化为"最近 N 轮"，跨重启的未压实轮次
  可能被永久跳过；
- 会话不终结时，蒸馏只依赖主题切换；长期不切换主题则 L3 永远为空；
- `touched`（终结向量修复）同样是进程内状态。

边界必须由记忆实现（组件）拥有——框架不拥有压实/蒸馏语义；不得把
未定义责任推给存储实现；不得增加每轮阻塞 I/O；必须给出崩溃与并发
窗口下的明确语义。

## Decision（决策）

### 1. 维护边界的持久化：L1 契约承载压实游标

`L1MemoryStore` 增加两个**必选**方法（破坏性变更，0.9.0）：

```rust
pub trait L1MemoryStore: Send + Sync + 'static {
    // 现有方法不变
    fn append(&self, entry: L1MemoryEntry) -> Result<(), MemoryStoreError>;
    fn recent(&self, scope: &MemoryScope, turns: usize)
        -> Result<Vec<L1MemoryEntry>, MemoryStoreError>;
    fn count(&self, scope: &MemoryScope) -> Result<usize, MemoryStoreError>;

    /// 尚未标记压实的轮次（旧→新）——跨重启的权威待压实集合。
    fn uncompacted(&self, scope: &MemoryScope)
        -> Result<Vec<L1MemoryEntry>, MemoryStoreError>;

    /// 把 `through`（批次末条 id）及其之前的轮次标记为已压实。
    /// 幂等：游标已越过、或 id 未知时为 no-op。
    fn mark_compacted(&self, scope: &MemoryScope, through: &str)
        -> Result<(), MemoryStoreError>;

    fn remove(&self, scope: &MemoryScope, id: &str) -> Result<bool, MemoryStoreError>;
    fn clear(&self, scope: &MemoryScope) -> Result<(), MemoryStoreError>;
}
```

- 游标描述轮次日志的消费位置，与日志同处一个存储：批次精确、推进
  原子、无跨存储一致性问题；不引入第五份存储。
- 必选而非默认实现：避免"忘记实现即静默退化"。
- 内置进程内默认实现同样实现两个方法（内存游标），行为不变。
- 组件删除进程内未压实计数器：每进程每会话首次归档时从
  `uncompacted(scope)` 初始化触发缓存（一次读），之后逐轮本地自增；
  触发时以 `uncompacted(scope)` 为权威批次——不再有"最近 N 轮"的
  退化路径。重启后首次触发即计入跨重启积压；积压已达阈值时立即补做。
- `append` 不变；每轮 I/O 不增加。

### 2. 蒸馏触发：压实时的批次年龄门槛（W1′）

- **窗口填满 / 重启补做**：压实总是执行；蒸馏仅当批次**最早轮次**
  （`batch.first().created_at`，批次旧→新排列）距当前时间达到沉淀
  窗口时执行。
- 未达龄的批次跳过蒸馏：其内容保留在 L2 条目中，并在后续蒸馏中
  作为 "Conversation entries" 上下文重新提供给提取器——不引入第二个
  游标，也不要求存储额外保留原文。
- **主题切换与会话终结**：不受窗口约束（显式语义边界，保持现有行为）。
- 沉淀窗口可配置，**默认 1 天**；上游消费方按产品需要设置（例如
  3 天）。默认不采用 0：把"每次压实即蒸馏"设为默认会让新近写入的
  内容过早沉淀为长期记忆；0 仍可显式配置（退化为"压实即蒸馏"）。
- 判定使用批次自带时间，无需额外持久化。

### 3. 并发与崩溃一致性：单游标、成功后推进、按会话串行、至少一次

- **推进时机**：压实的 L2 写入全部成功后 `mark_compacted`；蒸馏是
  同一任务的附加步骤，其失败上报 `Failed` 事实但不阻止推进（内容
  已由 L2 承接）。
- **串行化**：按会话维护 busy 守卫；任务运行期间的触发直接跳过，
  下一轮再触发。消除正常路径上的批次重叠。
- **批次上限**：单次维护处理至多 `l1_turns` 条待压实轮次，游标逐段
  推进；积压更大时由后续触发继续排空（摘要器输入与成本有界）。
- **崩溃/部分写入语义**：正常运行为恰好一次；数据写入成功与游标推进
  之间崩溃、L2 部分写入失败、或终结排空超时后与卡住任务重叠时，为
  **至少一次**——该批次会被重试，可能产生重复 L2 条目或版本抖动。
  failed 事实经框架可见；不假设跨存储事务。
- 游标单调：绝不先于数据写入推进（不做至多一次）。

### 4. 不变量

- 批次 = 持久化的待压实集合，永不退化为"最近 N 轮"；
- 游标只前进，且只在数据写入成功后前进；
- 框架零改动：核心不感知压实/蒸馏，不新增生命周期契约。

## Alternatives Considered（备选与否决）

1. **新增第五份维护状态契约**——否决：公开面 +1，且批次查询仍需 L1
   扩展，跨存储一致性成本更高；
2. **从 L2 条目派生边界（条目携带批次）**——否决：L2 淘汰、管理遗忘、
   空批次跳过都会使边界回退，导致重复处理；
3. **进程内计数 + 启动启发式对账（count / 时间戳）**——否决：无法
   可靠区分已压实与未压实，淘汰/时钟/同秒均产生歧义；
4. **字面时间窗（压实事件开关）**——否决：未达龄批次被跳过即永久
   失去作为原文批次被蒸馏的机会；
5. **滞后蒸馏游标（W1）**——否决：需要第二个持久化位置与窗口内原文
   保留，超出当前需求；W1′ 以 L2 承接达到相同目的；
6. **游标先行（至多一次）**——否决：崩溃即丢批次；
7. **批次 id + 幂等替换（接近恰好一次）**——否决：需扩展 L2 条目
   公开类型，替换与用户编辑/版本历史交互复杂，仍有残余窗口，当前
   需求未要求恰好一次；
8. **跨会话全局串行**——否决：维护单位是会话，全局锁无正确性收益。

## Consequences（后果）

**破坏项（0.9.0）**

- `L1MemoryStore` 新增两个必选方法；自定义持久化存储必须持久化每会话
  游标（可在快照/清单中增加一个字段，与既有 append 同一 fsync 批次）。
- 内置进程内默认实现同步补齐，行为不变。

**行为项**

- 维护跨重启可恢复：批次为持久化待压实集合，重启后首次使用即对账，
  积压达阈值立即补做；
- 压实仍总是执行；蒸馏新增批次年龄门槛（默认 1 天），主题切换/
  会话终结不变；
- 按会话串行维护；崩溃/部分写入窗口为至少一次（可能重复，文档说明）；
- 单次维护至多 `l1_turns` 条，逐段排空。

**边界（本 ADR 不做）**

- `touched` 保持进程内、尽力而为：重启后上一进程登记的终结向量修复
  不再执行（正常写入的向量不受影响）——记为开放项；
- 管理编辑与在途压实之间的既有竞态（压实的 `existing` 快照可能覆盖
  刚完成的编辑）——另行决策；
- 长期不再打开的会话不做启动扫描：积压在该会话下次使用或终结时处理；
- 不提供跨存储恰好一次；不改动框架生命周期。

## 验证要求

- 重启模拟（共享持久化测试存储）：重建 provider 后积压被正确压实/
  蒸馏，批次跨重启正确，正常路径无重复；
- 崩溃窗口：模拟 L2 写入失败 → 游标不推进 → 重试（记录的重复代价）；
- 并发：同会话多次触发被串行化（运行中跳过，下轮重试）；
- 沉淀窗口：默认 1 天，按批次最早轮次判定；显式设为 0 时退化为
  "压实即蒸馏"；主题切换/终结不受窗口影响；
- 默认实现回归：既有全量用例行为不变；
- 自定义存储契约一致性：参考持久化存储实现两个新方法并通过上述用例。
